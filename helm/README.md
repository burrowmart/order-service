# user-service Helm chart

Inherits all Kubernetes object templates from `platform-infra/helm/base-service`
via a chart dependency. Only service-specific values live here.

## Prerequisites

| Tool | Version |
|------|---------|
| Helm | ≥ 3.12 |
| kubectl | ≥ 1.28 |
| External Secrets Operator | installed in cluster |
| `aws-secrets-manager` ClusterSecretStore | pre-provisioned by platform-infra Terraform |

---

## Render (dry-run, no cluster required)

```bash
# 1. Fetch the base-service dependency (creates charts/base-service-0.1.0.tgz)
helm dependency update ./user-service/helm

# 2. Lint
helm lint ./user-service/helm

# 3. Render to stdout — inspect the full manifest before applying
helm template user-service ./user-service/helm

# 4. Render with a specific image tag (mirrors what CI does)
helm template user-service ./user-service/helm \
  --set base-service.image.tag=sha-$(git rev-parse --short HEAD)
```

---

## Deploy to EKS

```bash
# One-time: obtain cluster credentials (GitHub Actions uses OIDC; local dev uses this)
aws eks update-kubeconfig --name <cluster-name> --region <region>

# First install
helm upgrade --install user-service ./user-service/helm \
  --namespace user-service \
  --create-namespace \
  --set base-service.image.tag=sha-<git-sha> \
  --set base-service.irsaRoleArn=arn:aws:iam::<ACCOUNT_ID>:role/user-service-irsa \
  --wait

# Subsequent releases (idempotent; safe to run in CI on every push)
helm upgrade user-service ./user-service/helm \
  --namespace user-service \
  --set base-service.image.tag=sha-<git-sha> \
  --atomic \
  --timeout 5m
```

## Key values reference

| Value | Default | Notes |
|-------|---------|-------|
| `base-service.image.tag` | `latest` | CI sets this to the git SHA |
| `base-service.irsaRoleArn` | `arn:aws:iam::ACCOUNT_ID:role/user-service-irsa` | Replace after `terraform apply` |
| `base-service.secretsManagerPath` | `/prod/user-service` | Must contain: `MONGO_URI`, `RABBITMQ_URL`, `REDIS_URL`, `COGNITO_USER_POOL_ID`, `COGNITO_CLIENT_ID`, `JWT_SECRET` |
| `base-service.opaAddress` | `opa-pdp.opa-system.svc.cluster.local:9191` | OPA DaemonSet ClusterIP; `failure_mode_allow: false` enforced |
| `base-service.ingress.host` | `user-service.internal.archtenet.com` | Internal only — Cloudflare Tunnel entry point |
| `base-service.replicaCount` | `2` | HPA overrides at runtime (min 2, max 10) |

## Envoy / OPA authorization

Every pod runs an `envoy-pep` sidecar (port `8080`) that performs `ext_authz`
over gRPC to the OPA DaemonSet before forwarding any request to the `app`
container (port `3000`). The Envoy configmap is generated by the base chart
from `opaAddress` with `failure_mode_allow: false` — matching the policy in
`opa-policies/envoy/ext-authz.yaml`. A PDP crash results in **DENY**, never
open access.

The Kubernetes Service routes external traffic to port `8080` (Envoy), never
directly to the app container. All network paths:

```
Cloudflare Tunnel → nginx-internal Ingress → Service:80 → envoy-pep:8080
  → ext_authz gRPC → OPA DaemonSet:9191
  → app:3000 (on allow)
```

## Secrets

AWS Secrets Manager document `/prod/user-service` is synced into a k8s Secret
by External Secrets Operator every hour. The pod's `envFrom.secretRef` injects
all keys as environment variables. **No secret values appear in this chart.**

The ServiceAccount carries the IRSA annotation
`eks.amazonaws.com/role-arn: <irsaRoleArn>` so the pod's AWS API calls are
authenticated without static credentials.
